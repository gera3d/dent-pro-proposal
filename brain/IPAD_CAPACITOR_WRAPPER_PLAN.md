# iPad Capacitor Wrapper Plan

## Goal

Add a minimal native iPad wrapper around the existing PWA so the app can keep its current HTML, CSS, and JavaScript architecture while gaining access to hardware-only capabilities that Safari and Chrome do not expose to web pages.

The main native-only requirement is this:

- Physical `volume up` / `volume down` should trigger the existing camera shutter flow.

Everything else should stay as web-first as possible.

## What Stays Web

These parts should remain in the current web app without being rewritten:

- Main UI and routing in `index.html`
- Guided photo workflow
- Photo strip and session photo state
- Airtable / GHL / PDF / local draft logic
- Existing `capturePhoto()` behavior
- Existing `openCamera(category)` and `closeCameraModal()` flow

For this repo, the wrapper should treat the current web app as the product and the native code as a very small integration layer.

## What Moves Native

Only the device-level pieces that the browser blocks or handles poorly should move native:

- Listen for hardware volume button changes on iPadOS
- Forward a native shutter event into the web layer
- Optionally expose native haptics
- Optionally expose a native camera mode later if browser camera behavior becomes a constraint

The first version should not replace the current web camera implementation. It should only add a native event bridge.

## Minimal Architecture

### 1. Capacitor App Shell

Create a small Capacitor iOS app that loads the existing app inside a `WKWebView`.

Expected new top-level files:

- `package.json`
- `capacitor.config.ts`
- `ios/` project generated by Capacitor

Recommended web asset strategy:

- Bundle the current app files locally into the native app for stable releases
- Keep the browser PWA as a separate deployment target
- Do not rely on service worker behavior inside the native shell as the primary offline mechanism

### 2. Native Bridge Plugin

Add one custom Capacitor plugin, for example:

- `DentCameraBridgePlugin`

Responsibilities:

- Start listening for volume changes when the camera modal is open
- Stop listening when the camera modal closes
- Emit a `nativeVolumeShutter` event to JavaScript

### 3. Web Bridge Layer

Add a thin JavaScript adapter in the web app so native integration is optional.

Proposed shape:

```js
window.DentNative = {
  isNativeWrapper: false,
  startVolumeShutter() {},
  stopVolumeShutter() {}
};
```

When running inside Capacitor, those methods are replaced by plugin calls.

### 4. Existing Camera Flow Hooks

The native wrapper should plug into the current functions instead of creating a second camera state machine.

Use these existing entry points:

- `openCamera(category)`
- `closeCameraModal(savePhotos = true)`
- `capturePhoto()`
- `pulseCameraShutter()`

Current camera lifecycle already exists in `index.html`, so the native layer should only signal when to fire the shutter.

## Native-to-Web Event Flow

### Open Camera

When the app calls `openCamera(category)`:

1. Web app opens the current modal.
2. Web app calls `DentNative.startVolumeShutter()` if available.
3. Native layer begins listening for hardware volume changes.

### Volume Button Press

When the technician presses a physical volume button:

1. Native iOS detects the hardware volume change.
2. Native plugin emits an event such as `nativeVolumeShutter`.
3. Web app receives the event.
4. Web app checks `isPhotoCameraModalOpen()`.
5. Web app calls `pulseCameraShutter()`.
6. Web app calls `capturePhoto()`.

### Close Camera

When the app calls `closeCameraModal()`:

1. Web app closes the modal.
2. Web app calls `DentNative.stopVolumeShutter()` if available.
3. Native plugin stops listening.

## Proposed JavaScript Integration

This is the intended shape, not production code yet:

```js
function setupNativeWrapperBridge() {
  const hasCapacitor = !!window.Capacitor;

  window.DentNative = {
    isNativeWrapper: hasCapacitor,
    async startVolumeShutter() {
      if (!hasCapacitor) return;
      await Capacitor.Plugins.DentCameraBridge.startVolumeShutter();
    },
    async stopVolumeShutter() {
      if (!hasCapacitor) return;
      await Capacitor.Plugins.DentCameraBridge.stopVolumeShutter();
    }
  };

  if (hasCapacitor) {
    Capacitor.Plugins.DentCameraBridge.addListener('nativeVolumeShutter', () => {
      if (!isPhotoCameraModalOpen()) return;
      pulseCameraShutter();
      capturePhoto();
    });
  }
}
```

This preserves the current browser behavior while enabling native-only behavior when available.

## iOS Implementation Notes

### How Volume Detection Usually Works

iOS does not provide a clean public API that simply says "volume button pressed for camera shutter" for a web page. In a native wrapper, the usual pattern is:

- Observe system output volume changes
- Distinguish intentional button presses from app startup state
- Reset or manage the volume side effect so the hardware buttons remain usable

This is the part that must be implemented carefully in Swift.

### Important Constraint

The wrapper is viable, but the hardware button implementation is the riskiest part of the whole design. The web layer is the easy part. The iOS native event handling is the part that needs the most care and real-device testing.

### Safer Alternative if Apple Pushes Back

If direct hardware volume handling becomes fragile or review-sensitive, keep the Capacitor wrapper but move only the capture screen to a native camera controller. Then native code can take the image directly and hand the JPEG back to the existing web workflow.

That is a larger step than the minimal bridge, but still far smaller than a full rewrite.

## What Happens to the PWA

The PWA does not have to go away.

Recommended setup:

- Browser PWA remains available for desktop and general access
- Native iPad wrapper becomes the preferred field-tool build

That gives you:

- Fast web iteration for most features
- Native hardware integration where it matters

## Service Worker Impact

Current browser caching logic lives in `service-worker.js`.

Inside the native wrapper:

- Service worker support is not the thing you should rely on for app packaging
- The native app already ships the web assets locally
- Browser PWA caching and native packaged assets should be treated as two separate delivery modes

Practical recommendation:

- Keep `service-worker.js` for the browser PWA
- Treat Capacitor builds as bundled releases

## Minimal File/Module Plan

### New Native/App Files

- `package.json`
- `capacitor.config.ts`
- `ios/App/...`
- `ios/App/App/plugins/DentCameraBridgePlugin.swift`

### Small Web Additions

Add one small bridge module or inline block that:

- Detects Capacitor
- Starts native volume listening from `openCamera(category)`
- Stops native volume listening from `closeCameraModal()`
- Listens for `nativeVolumeShutter`
- Reuses `pulseCameraShutter()` and `capturePhoto()`

## Recommended Delivery Phases

### Phase 1

Create the Capacitor shell and prove the current app loads on iPad.

Success criteria:

- Existing app runs inside the wrapper
- Camera permissions work
- Current tap-to-capture flow still works

### Phase 2

Add the custom native plugin and wire volume-button events into the current shutter path.

Success criteria:

- Physical volume buttons trigger `capturePhoto()` only while the camera modal is open
- No stray captures outside the modal
- No double-fire on long press

### Phase 3

Harden field behavior.

Success criteria:

- Resume/background works
- Permissions are stable
- Audio volume side effects are acceptable
- TestFlight install is usable by technicians

## Downsides Specific To This Wrapper Plan

### 1. App Store and Signing Overhead

You will need:

- Apple Developer account
- Xcode signing and provisioning
- TestFlight / App Store distribution workflow

### 2. Native QA Burden

You now have two execution environments:

- Browser PWA
- Native iPad wrapper

Camera and upload behavior must be tested in both.

### 3. Update Model Changes

Today, a web deploy updates immediately.

With a wrapper:

- Web-only changes can still move fast if the native shell loads bundled web assets that you rebuild frequently
- Native capability changes require a new app build

### 4. Hardware Volume Handling Risk

This is the part most likely to need iteration. It is also the entire reason for doing the wrapper.

## Recommendation

The smallest sensible version for this repo is:

- Keep the current web camera UI
- Add a Capacitor shell
- Add one custom native plugin for hardware shutter events
- Reuse `capturePhoto()` instead of replacing the camera flow immediately

If that proves unstable on real devices, the next step should be a native capture screen only, not a full native rewrite.

## Immediate Next Build Step

If moving forward, the first implementation task should be:

- scaffold Capacitor in this repo
- generate the iOS project
- add a JavaScript bridge stub
- prove the current app runs inside iPad simulator / device

Only after that should the hardware volume plugin be added.
